================================================================================
RELATÓRIO DE ANÁLISE DO PROJETO - SISTEMA DE MONITORAMENTO SAMAE
================================================================================

1. VISÃO GERAL
--------------
O projeto SAMAE é um sistema de monitoramento de reservatórios projetado para 
acompanhar níveis e vazões de água em tempo real (focado no período da madrugada). 
Ele fornece uma interface visual para operadores e engenheiros avaliarem o 
status operacional, identificarem alertas e analisarem tendências históricas.

2. ARQUITETURA TÉCNICA
----------------------
O sistema utiliza uma arquitetura baseada em arquivos JSON para armazenamento, 
eliminando a necessidade de um servidor de banco de dados tradicional.

- Backend (Ingestão): Script Python para processamento de planilhas Excel.
- Frontend (Interface): SPA (Single Page Application) em HTML/CSS/JS Vanilla.
- Visualização: Gráficos interativos utilizando a biblioteca Chart.js.
- Dados: Estruturados em arquivos JSON mensais para eficiência de carregamento.

3. ESTRUTURA DE ARQUIVOS E COMPONENTES PRINCIPAIS
-------------------------------------------------
/ (Raiz)

4. FUNCIONAMENTO GERAL E FLUXO DE DADOS
---------------------------------------
1. Processamento: O script Python lê as planilhas do SAMAE, extrai leituras de 
   nível e vazão entre 00:15 e 05:15, e ajusta as datas (+1 dia) para refletir 
   o dia do boletim.
2. Ingestão: Os dados são salvos em dados_historicos/ e o indice_datas.json é 
   atualizado.
3. Carregamento: Ao abrir o dashboard, o app.js carrega o índice e baixa apenas 
   os meses necessários via Fetch API.
4. Regras de Negócio: O sistema avalia cada reservatório:
   - Nível: < 60% (Atenção), < 50% (Crítico).
   - Vazão: Variação > 20% (Atenção), > 35% (Crítico) contra base histórica.
5. Visualização: O usuário interage com o "Boletim Operacional", filtros de 
   grupos e abas de "Análise" e "Engenharia" para auditoria detalhada.

5. PRINCIPAIS RECURSOS
----------------------
- Boletim Operacional: Resumo instantâneo (Normais, Atenção, Críticos, Incompletos).
- Comparação Flexível: Permite comparar vazões com os últimos 7 dias, 30 dias 
  ou o mesmo dia da semana no mês anterior.
- Análise de Engenharia: Visão técnica para identificar falhas de sensores ou 
  leituras ausentes.
- Design Responsivo: Suporte a temas claro/escuro e visualização em diferentes 
  dispositivos.

6. ESCOPO DE DESENVOLVIMENTO E DIRETRIZES ATUAIS
------------------------------------------------
Para garantir a entrega de valor imediata e a excelência técnica na operação de 
campo, foram estabelecidas as seguintes prioridades:

6.1. Foco na 'Visão Operacional'
Todos os esforços atuais de desenvolvimento, interface e UX estão concentrados 
exclusivamente na aba "Visão Operacional". O objetivo é maximizar a usabilidade 
em campo, a clareza dos alertas e a facilidade de leitura para os operadores 
do SAMAE. As demais abas (Análises, Engenharia e funções avançadas) permanecem 
em segundo plano e serão tratadas de forma incremental em fases futuras.

6.2. Estratégia de Ingestão de Dados
Nesta fase inicial, o sistema consumirá exclusivamente os dados locais em 
formato JSON gerados pelo script Python a partir das planilhas Excel. 

Diretriz de Evolução: Futuramente, após a aprovação e definição do formato pelo 
SAMAE de Jaraguá do Sul (seja via API REST, WebSockets, telemetria por rádio ou 
outro meio), a camada de ingestão de dados (localizada principalmente no 
módulo `app.js`) será adaptada para a nova fonte. Graças à arquitetura modular 
e ao desacoplamento das regras de negócio, essa migração ocorrerá sem 
impactar a interface ou a lógica de cálculo da Visão Operacional.

7. ANÁLISE CRÍTICA E ROADMAP DE EVOLUÇÃO (VISÃO SENIOR)
-------------------------------------------------------
A arquitetura atual é um excelente exemplo de MVP (Produto Mínimo Viável) de 
baixo custo e alta entrega. O uso de JSONs estáticos elimina a complexidade de 
um banco de dados relacional e facilita o deploy. No entanto, o cenário de 
migração para "Tempo Real" exige mudanças estruturais profundas.

6.1. Avaliação da Arquitetura Atual
- Acoplamento: Alto acoplamento entre o schema de dados gerado pelo Python e o 
  consumo no Frontend. Qualquer mudança na planilha Excel exige alteração em 
  duas linguagens diferentes.
- Estado Global: O Frontend depende fortemente do `window.bancoDeDados`. Embora 
  funcional, isso dificulta testes unitários e pode causar race conditions em 
  atualizações assíncronas complexas.
- Manutenibilidade: A lógica de negócios em `regrasNegocio.js` está bem isolada, 
  o que é um ponto positivo (Single Responsibility Principle).

6.2. Riscos Arquiteturais
- Escalabilidade Vertical: Com o passar dos anos, o número de arquivos JSON em 
  `dados_historicos/` crescerá exponencialmente. O carregamento de meses inteiros 
  para exibir um único dia se tornará ineficiente.
- Concorrência e Integridade: Arquivos estáticos não suportam gravações 
  concorrentes de forma nativa. Se dois processos tentarem atualizar o índice, 
  pode haver corrupção de dados.
- Latência de Tempo Real: O modelo atual de "pull" (cliente requisita arquivo) 
  não é ideal para tempo real. O overhead de requisições HTTP para arquivos 
  estáticos a cada poucos segundos sobrecarregará o cliente.

6.3. Recomendações Técnicas para Evolução
- Camada de API (Decoupling): Introduzir um backend (FastAPI ou Node.js) que 
  atue como um "Data Provider". O Frontend não deve saber onde os dados estão 
  salvos, apenas consumir uma API REST ou GraphQL.
- Transição para Time-Series Database: Substituir os JSONs por um banco de 
  dados focado em séries temporais (ex: InfluxDB ou TimescaleDB/PostgreSQL). 
  Isso permitiria consultas agregadas complexas em milissegundos.
- Implementação de WebSockets/SSE: Para o tempo real, o servidor deve "empurrar" 
  os dados para o Frontend (Push model) via WebSockets ou Server-Sent Events, 
  evitando o polling constante.
- Gerenciamento de Estado no Frontend: Evoluir o SPA Vanilla para uma 
  arquitetura baseada em Componentes e um Store (ex: padrão Redux/Zustand, 
  mesmo em JS puro), isolando a visualização dos dados da sua manipulação.

6.4. Conclusão da Análise
O projeto está pronto para a próxima fase. A separação clara entre 
`regrasNegocio.js` e `ui.js` permitirá que a transição para um backend em 
tempo real ocorra sem reescrever a lógica de alertas, bastando trocar o 
módulo de ingestão de dados (`app.js`).
