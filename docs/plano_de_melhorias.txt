1. OBJETIVO DO DOCUMENTO
--------------------------------------------------------------------------------
Este documento registra as sugestões de melhorias técnicas e de interface para 
a aba "Visão Operacional", bem como o histórico de implementação no modelo 
"COMO ESTAVA" vs "COMO FICOU", garantindo auditabilidade e controle de versão 
das entregas focadas nos operadores do CCO.

--------------------------------------------------------------------------------
2. MATRIZ DE MELHORIAS (PLANO VS IMPLEMENTAÇÃO)
--------------------------------------------------------------------------------

[ITEM 01] - SELO DE STATUS E HORA DO BOLETIM
- Status: 🟢 Concluído
- Categoria: Usabilidade / Segurança da Informação
- Como Estava:
    * A data/hora do boletim carregado ficava dispersa ou subentendida nos dados do JSON.
    * O operador precisava procurar manualmente para saber se estava olhando o boletim da madrugada.
- Como Ficou:
    * [Badge de Status e Hora]: Implementado o selo/badge destacado no cabeçalho superior (`.bulletin-status-badge`) exibindo claramente a indicação "Boletim Operacional" acompanhada da data e horário exatos obtidos dinamicamente dos dados (ex: `13/10/2026 - 05:15`).
    * [Indicador Visual de Validade]: Integrado um indicador visual com ponto luminoso verde pulsante (`.bulletin-dot` com `@keyframes pulsarVerde`), garantindo confirmação visual instantânea de que o operador está visualizando dados válidos e atualizados.
    * [Sincronia Dinâmica]: O selo atualiza-se automaticamente sempre que o operador altera a data consultada no seletor do painel operacional.

--------------------------------------------------------------------------------

[ITEM 02] - HIGHLIGHT E ANIMAÇÃO PARA ALERTAS CRÍTICOS
- Status: 🟢 Concluído
- Categoria: Interface (UI) / Leitura Rápida
- Como Estava:
    * Cards de reservatórios em alerta usavam apenas cores estáticas básicas (amarelo e vermelho).
    * Em monitores grandes do CCO (TVs de plantão), o alerta podia passar despercebido à distância.
- Como Ficou:
    * Implementada borda e sombra pulsante via CSS Keyframes (@keyframes pulsarCritico) no botão global de "Críticos", acionada de forma totalmente automatizada quando a contagem de incidentes é maior que zero (registros.length > 0).
    * Optou-se por manter a animação restrita ao botão indicador para evitar poluição visual e fadiga dos operadores no CCO. Ao ser clicado, o botão filtra e isola imediatamente os cards críticos na tela, garantindo leitura rápida, foco cirúrgico no problema e uma interface limpa.

--------------------------------------------------------------------------------

[ITEM 03] - MODO OPERACIONAL CCO (TELA CHEIA / KIOSK MODE)
- Status: 🟢 Concluído
- Categoria: Experiência do Usuário (UX) / Engenharia de Layout

- Como Estava:
    * O painel operava com uma interface web padrão carregando barras de navegação tradicionais do navegador (abas, favoritos e barra de endereços).
    * O layout do site possuía margens laterais fixas largas e elementos textuais secundários que disputavam espaço físico útil.
    * O visual do botão de teste utilizava um caractere emoji genérico (📺) e rótulos de texto longos, destoando do padrão sóbrio de sistemas industriais e ocupando espaço excessivo no cabeçalho.
    * Em monitores grandes e TVs de plantão do CCO, o espaço vertical e horizontal precioso era desperdiçado com componentes que não agregavam valor à leitura rápida dos operadores à distância.

- Como Ficou:
    * [Layout Expansível]: Implementado sistema responsivo avançado via classe controladora no body (`body.modo-cco-ativo`). Quando acionado, o CSS remove margens, omite elementos secundários de texto e estica a grade principal de reservatórios para ocupar 100% da área física útil da tela.
    * [Fullscreen API]: Integrado mecanismo nativo do navegador para ocultar instantaneamente o frame externo do software (abas e cabeçalhos do navegador), simulando uma aplicação de quiosque dedicada (Kiosk Mode).
    * [Sincronia por ESC]: Configurado ouvinte de evento global (`fullscreenchange`) para interceptar saídas manuais do operador via teclado (tecla ESC), limpando os estados da interface de forma transparente.
    * [Simetria e Design System]: O botão foi transformado em um container quadrado perfeito de 44px com bordas arredondadas de 12px e efeito hover suave, replicando cirurgicamente as propriedades visuais do seletor de tema escuro nativo do painel.
    * [Ícones Vetoriais Avançados]: Substituído o emoji por vetores SVG minimalistas de traço fino (estilo Lucide). O botão agora alterna dinamicamente entre o ícone de monitor industrial (Modo CCO) e o ícone de painel dividido (Modo Padrão), acompanhando a cor do texto (`var(--text-color)`) e recebendo destaque em azul (`var(--accent-color)`) na borda quando ativo. Os elementos foram agrupados no canto superior direito (`justify-content: flex-end`), gerando um cabeçalho limpo, técnico e profissional.

[ITEM 04] - CABEÇALHO FIXO E FILTROS RÁPIDOS (STICKY HEADER)
- Status: 🟡 Planejado
- Categoria: Agilidade Operacional
- Como Estava:
    * Ao rolar a página para verificar reservatórios no fim da lista, o operador perdia o acesso 
      visual ao resumo geral e aos botões de filtro de grupos.
- Como Ficou:
    * [Aguardando implementação]
    * Proposta: Barra superior fixa (sticky) contendo os contadores globais (Normais, Atenção, 
      Críticos, Incompletos) e seletores rápidos de zona/grupo sempre visíveis.

--------------------------------------------------------------------------------

[ITEM 05] - ABSTRAÇÃO DA CAMADA DE CONSUMO DE DADOS
- Status: 🟢 Concluído
- Categoria: Arquitetura de Código
- Como Estava:
    * Requisições 'fetch' aos arquivos JSON locais (`dados_historicos/`) ligadas diretamente à 
      lógica de inicialização do frontend em `app.js`.
- Como Ficou:
    * [Criação do Serviço `src/apiClient.js`]: Implementado o módulo padronizado `window.ApiClient` encarregado de encapsular todas as requisições HTTP e o carregamento assíncrono dos arquivos JSON mensais e índices (`indice_datas.json`).
    * [Isolamento Arquitetural]: A camada de frontend em `app.js` agora consome dados exclusivamente através de `ApiClient`, desacoplando completamente a lógica de apresentação e regras de negócio da infraestrutura de rede.
    * [Preparação para Futura API]: Na transição futura do SAMAE para API REST, WebSockets ou Rádio, bastará alterar os métodos de `src/apiClient.js`, sem necessidade de modificações em `ui.js`, `graficos.js` ou `regrasNegocio.js`.

--------------------------------------------------------------------------------

[ITEM 06] - RESUMO RÁPIDO DE PASSAGEM DE PLANTÃO
- Status: 🟡 Planejado
- Categoria: Utilidade Operacional
- Como Estava:
    * O operador precisava anotar manualmente os reservatórios que apresentaram alteração no turno.

    * [Aguardando implementação]
